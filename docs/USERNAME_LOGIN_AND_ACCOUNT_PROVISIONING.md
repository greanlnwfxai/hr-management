# Username Login and HR Account Provisioning

## Overview

T-050 adds username-based login and HR-controlled account provisioning to the HR Management System. Users can now authenticate with either a username or email address. HR/Admin personnel can create login accounts for employees with system-generated temporary passwords.

---

## Login Identifier Behavior

`POST /auth/login` accepts a JSON body with:
- `login` (preferred) — username or email
- `email` (legacy) — treated identically to `login`
- `password` — required

Resolution logic:
1. Resolve identifier: `login ?? email ?? ''`
2. Trim and lowercase
3. If identifier contains `@` → search by email
4. Otherwise → search by username
5. Reject if `isActive = false`

Both formats remain valid for backward compatibility:
```json
{ "login": "admin", "password": "admin1234" }
{ "login": "admin@hr.local", "password": "admin1234" }
{ "email": "admin@hr.local", "password": "admin1234" }
```

The response includes `username` in the user object and JWT payload.

## Username Policy

| Rule | Detail |
|------|--------|
| Allowed characters | `a-z 0-9 . _ -` |
| Case | Lowercase only |
| Spaces | Not allowed |
| Thai characters | Not allowed |
| Must be unique | Yes (database unique constraint) |
| Regex | `^[a-z0-9._-]+$` |

### Username Suggestion Rule

When English first and last name fields are available:
- Format: `{first letter of lastName}.{firstName}` (all lowercase)
- Example: Pichai Jaijit → `j.pichai`
- Returns `null` if no usable Latin characters are present

The system suggests a username during provisioning, but HR must confirm or edit it before the account is created.

---

## Password Generation

Temporary passwords are generated by `src/common/password.util.ts`:
- Exactly 8 characters
- At least 1 uppercase English letter (A-Z, excluding ambiguous chars)
- At least 1 lowercase English letter (a-z, excluding ambiguous chars)
- At least 1 digit (2-9, excluding 0/1)
- At least 1 special character from `!@#$%^&*`
- Cryptographically secure via `crypto.randomInt`
- Securely shuffled

The temporary password is **shown only once** in the API response. It is never persisted in plain form — only the bcrypt hash (cost 10) is stored.

## HR Account Provisioning Flow

### Create Account

```
POST /employees/:id/account
Authorization: Bearer <admin-token>
Content-Type: application/json

{
  "username": "j.pichai",
  "role": "EMPLOYEE",
  "email": "pichai.j@company.com"   (optional)
}
```

Response (201):
```json
{
  "userId": "uuid",
  "employeeId": "uuid",
  "username": "j.pichai",
  "email": "emp_<id>@hr.local",
  "role": "EMPLOYEE",
  "mustChangePassword": true,
  "temporaryPassword": "X7#mqa2B"
}
```

- `temporaryPassword` is shown **once only** — copy it immediately
- `mustChangePassword` is set to `true`
- If the employee already has a linked User account, it is updated (not duplicated)
- Required roles: `SUPER_ADMIN`, `HR_ADMIN`

### Reset Password

```
POST /employees/:id/account/reset-password
Authorization: Bearer <admin-token>
```

Response (201): Same shape as above. A new temporary password is generated and returned once.

---

## JWT Payload

Tokens now include:
```json
{
  "sub": "user-uuid",
  "email": "admin@hr.local",
  "username": "admin",
  "role": "SUPER_ADMIN",
  "employeeId": "employee-uuid-or-null"
}
```

`GET /auth/me` returns the same fields.

## Security Notes

- All error messages for invalid credentials use the same generic text: `"Invalid credentials"` — no enumeration of whether username or email exists
- Rate limiting remains in effect on `POST /auth/login`
- Passwords are hashed with bcrypt (cost 10)
- Plain passwords are never logged or persisted
- Inactive users (`isActive = false`) are rejected at login
- `mustChangePassword` flag is available for future first-login enforcement

---

## Known Limitations

- **First-login password change flow** is not yet implemented. `mustChangePassword` is tracked but the enforcement UI is a future task.
- **Email invite flow** is not implemented. HR must manually communicate the temporary password to the employee.
- **SSO / MFA** is not implemented.
- If an employee has only Thai names with no Latin equivalents, username suggestion returns `null` and HR must enter the username manually.
- The auto-generated fallback email for account provisioning (`emp_<id>@hr.local`) is a placeholder — HR should provide a real email when provisioning.
